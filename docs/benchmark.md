| 항목 | 목표(중간값) | 상한 |
|------|-------------|------|

| 동시 반납 3건일 때 | 같음 | 같음 |

## 측정 방법

```bash
python tools/build_vit_onnx.py --out .data/models/vit-s14-448x336.onnx   # DINOv2-S와 같은 구조
python -m bench.bench_compare --backbone .data/models/vit-s14-448x336.onnx --runs 12 \
    --threads 0 2 --long-side 1024 1280 1600 --concurrency 1 3 --out bench-result.json
```

- 입력: 합성 장면을 작업본 크기(2560×1920 JPEG)로 만든 기준 1장 + 반납 3장(스티커, 스크래치, 손상 없음)
- 기준 특징은 미리 계산해 메모리에 올린 상태(운영에서 `/prefetch`가 하는 일)
- 모델: DINOv2 ViT-S/14와 **구조가 같은** 무작위 가중치 ONNX(입력 448×336 → 32×24 패치).
  속도는 구조로 정해지므로 공식 가중치와 같다. 이 환경에서는 공식 가중치 서버 접속이 막혀 있어 이 방법을 썼다.

### 읽는 법과 결론

- **4 vCPU에서도 컷 1장 0.5초(목표 5초의 1/10).** 동시 3건이어도 p95 1.7초. CPU만으로 목표를 넉넉히 맞춘다.
- 동시 처리가 많을 때는 **요청당 스레드를 줄이는 편(2)이 낫다**: 동시 3건 p50 1212 → 857ms. 스레드끼리 CPU를 뺏지 않기 때문이다.
  운영 파드(CPU 4~6)의 시작 값: `INTRA_OP_THREADS=2`, `MAX_CONCURRENT_COMPARES=2`.
- 해상도를 1600으로 올리면 SSIM·정렬이 늘어 약 2배. 가는 스크래치 재현율이 부족할 때만 올린다(평가 세트로 결정).
- 사전 계산(대여 시점, GrabCut 포함)은 0.4~0.6초이고 직원이 기다리지 않는다.
- 업로드(LTE 1초 내외)와 api 왕복을 더해도 컷별 결과는 2초 안팎으로 예상한다. 실제 운영 CPU에서 다시 잰다.
